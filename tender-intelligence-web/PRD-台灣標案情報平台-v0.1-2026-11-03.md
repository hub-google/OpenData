## 0. 版本判讀及產品原則

本文標記：
- **競品已公開**：網站可見選單／方案／FAQ 或功能說明。這不必然表示登入後完整實測成功。
- **競品規劃**：網站明確標註「即將推出／規劃中」，不能算現有功能。
- **本產品規劃**：本 PRD 要做的功能，不表示已實作。
- **資料待驗**：來源完整率、欄位、授權或成本未充分證實，必須經資料驗收才能上線。

四個產品原則：
1. **基本標案查詢不強迫登入、不收費**；收費重點是用戶的省時、省漏案、精準情報、文件工作流與團隊效率。
2. **任何數字都要能追到原公告及計算方法**，不把缺值填零、不拿模擬案例充當真實標案。
3. **不宣稱能預測尚未公開的底價、得標率或識別「內定」**；所謂機會分數只代表使用者適配度，異常提示只提醒人工查核。
4. **自助 SaaS**：讓用戶自己完成搜尋、訂閱、設定條件、上傳文件、付款與管理；不把人工代標、顧問客製接案設成主要收入來源。
5. **客服僅兩個管道**：站內 AI 即時客服、問卷式問題回報與真人**站內**回覆，不設 Email 客服或人工 Email 回覆；與會員驗證／標案通知 Email 不衝突。
6. **安全的一鍵測試**：公開站提供無須輸入帳密的獨立測試帳號，測試客服工單及管理權不得觸及正式客戶資料。

## 2. 產品定位與目標

### 2.1 核心價值主張

> 「不只告訴你今天有哪些標案，而是讓你每天自動收到適合公司、真正來得及投的案；點入後有歷史成交價、機關／競爭者情報、資格檢核、標單摘要與送件待辦。」

### 2.2 目標客群（台灣）

1. **中小型供應商老闆**：一人同時做銷售與投標，希望少看雜訊、快速判斷適配／截止。
2. **負責政府案的業務／PM**：關注競品、招標更正、歷史機關需求，想交辦文件與任務。
3. **固定投標的公司業務團隊**：需多人協作、商機管線、文件與進度、帳號權限。
4. **第一次投標的小型商家**：需要白話解釋政府採購、資格／押標金／共同供應契約等規範。

### 2.3 不服務的主要需求

- 不替客戶代標、代送件、提供公關關係或人工撰寫整份標書。
- 不宣稱 AI 能識別機關「內定」、「陪標」、「綁標違法」；僅做有依據的條款異常提示。
- 不保證得標或自動提交官方採購系統。
- 不開發超出合法存取權限的全站爬蟲，亦不代替官方電子領標、押標金付款機制。

### 2.4 成功條件

- 用戶能在一個流程完成「找到符合業務的案→讀懂條件→儲存決策→收到異動與截止提醒」。
- 主要非 AI 查詢免費而且優於官方操作體驗；使用者願意為通知準確性、文件整理與團隊工作付費。
- 所有公告版本、統計與 AI 判讀可以連回來源。

## 3. 主要使用流程

### 3.1 訪客（免費、不登入）

開啟首頁 → 搜尋「校園網路設備」→ 篩選「仍招標、履約台北／新北、100–1000 萬」→ 檢視列表／機關／預算／截止日／更新時間 → 開一案看**全部可合法公開的公告欄位**、修正歷史、同類案件、官方連結 → 直接前往政府電子採購網。

未登入也必須能搜尋、看詳情、查看來源，不應遮住政府已公開的標案名稱、機關與案號逼人充值。

### 3.2 免費會員

註冊（Email magic link 或 Google；LINE 綁定為選用）→ 建立公司產業輪廓（選填，若提供統編，先查其合法公開資訊）→ 儲存 1 條搜尋條件、收藏 10 案 → 每日 Email 摘要 → 標案變更及截標時間可在站內查看。

### 3.3 付費個人

使用者先設定能力標籤、金額、地區、資格與排除詞 → 每天首頁直接顯示適配 Top 案 → 點開案例看「為什麼適合／哪裡不符」→ 讀機關與廠商歷史 → 訂閱 LINE／Email 即時更新 → 上傳合法取得的招標文件 → AI 生成有頁碼引用的資格／評選／清單 → 儲存決策與待辦。

### 3.4 團隊使用者

由管理者訂閱 → 建立公司工作區 → 邀請成員 → 管理者設定監控規則及信用額度 → 業務指派案件 → PM 維護階段／附件／待辦 → 截止前自動提醒 → 結案記錄是否投標、得標結果與原因。

### 3.5 站內客服流程（新增）

任意頁右下角懸浮「客服中心」→「AI 客服」或「問題回報」。AI 提問與實際回覆均儲存於資料庫；Gemini 金鑰無法安全取得時，仍儲存對話並固定回「AI 客服功能開發中」。AI 無法解答可按「改由真人處理」，帶入先前對話→填問題類型、主旨、說明、影響使用勾選→送出後產生工單編號→「我的紀錄」查看狀態、真人回覆與後續留言。匿名訪客可在同瀏覽器查詢；經驗證的正式會員可跨裝置查詢。人工回覆只在網站內，不發客服 Email。

### 3.6 一鍵測試登入及客服演練（新增）

未登入時點網站頂端或帳戶區的「測試帳號一鍵登入」→ 透過 Supabase Anonymous Auth 建立每人獨立測試身分，**無須輸入 Email／密碼**→ 自動開啟隔離的「測試客服後台」→ 系統預設 2 筆示範工單（待處理、已回覆）→ 可查看、回覆、變更狀態及重設示範工單。此身分不是真實客服管理員，只能存取自己 `is_demo=true` 的測試資料；不得看正式客戶或其他測試者的資料。正式會員若已登入，不可無提示地切換為測試身分；匿名測試身分通常僅能在原瀏覽器持續使用。

## 7. 真正能收費的加值模組

### V1. 「每天值得追的標案」精準商機雷達（主力賣點）

**輸入**：公司提供的產品／服務、合法公開歷史得標類別、可履約縣市、可承接金額、需要排除的工作、資格／實績偏好。

**輸出**：
- 今日 Top N 高適配新公告、即將截止且來得及準備案件。
- 每案顯示「符合理由」「可能不符」「還缺什麼資料」。
- 一鍵標記：追蹤、準備投標、放棄及原因（改善下一輪匹配）。
- 使用者可指定競爭者或目標機關追蹤。

**關鍵驗收**：能手動反饋誤判；檢索結果可追溯；不能將公司能力單憑名稱推斷為擁有資格。

### V2. 機關採購與重購情報

- 按年度／採購類別／月份觀察機關採購金額、頻率、平均與中位數。
- 過往得標商排行及集中度；只把具投標者資料的案件納入「投標勝率」分母。
- 推估「可能再次採購」時顯示歷次日期、週期樣本、現有契約期限、是否有續約選項、可信度。
- 允許訂閱「某機關又招類似設備」事件。
- 不以統計訊號保證未來一定招標。

### V3. 廠商／競爭者情報

- 以統編優先識別廠商，統編缺失時保留不確定匹配。
- 顯示投標／得標記錄、得標額、主要機關、品類、成長變動。
- 同場競標比較：只有官方資料**明列全部投標者**的案子才能計算；未記載者不推論。
- 公司間關係資料若來自合法公開公司登記，需註明時間與來源；同地址或姓名**不能直接推論串標**。
- 競品近期得標／參與新案提醒。

### V4. 成交價、底價與報價分析

輸出同類採購的可比樣本、金額分布、預算比 `decision_amount / budget`、有公告底價時的底價比，按機關／類別／決標方式／規模／年份分層。

核心要求：
- 同規格／數量／契約年期／維護內容不可直接混合。
- 多得標者／複數決標和單價契約不能用同一總額公式亂算。
- 每個報價區間列資料樣本數 n、中位數、四分位、來源案件。
- 樣本量不足時不產生「推薦報價」，不稱能預測未公開底價。

### V5. AI 標單解析

使用者**合法取得** PDF/DOCX/XLSX／附檔後上傳，依實際格式支援能力解析：
- 資格：統編、營業項目／實績／保險／資格證明等。
- 時間：領標、投標截止、開標、現勘、簡報、履約期。
- 財務：押標金、履約保證金、付款／驗收條件、違約金。
- 規格：交付項目、數量、設備規格、服務水準。
- 評選：配分、最低合格標準、必備附件。
- 交付：資格與服務建議書清單、投標檢核表。
- **引用**：每項抽取附原始檔名、頁數／表格位置；使用者能點回原文。
- 文件變更：上傳新公告版本後，顯示本次增修的條款差異；提醒重跑資格檢核。

**失敗機制**：掃描品質太差或文件缺頁，標明無法確定、請人工核對；AI 不填補未知的法規條款。

### V6. 投標決策（Go / No-Go）

**硬性閘門**：已截止、法定資格不符（有證據）、無法履約、超過公司承作範圍，顯示「需處理／不建議」而非直接假設一定無法投。

**可解釋分數（0–100）**：
- 類別及文本適配 25
- 公司資格與實績吻合 25
- 履約地與規模適合 15
- 可準備時間與交付條件 15
- 可比歷史競爭強度 10
- 使用者商業偏好／毛利假設 10

**分數意義**：這是「此公司對此標案的**適配程度**」，**不是得標機率**。未知欄位必須分開顯示 evidence coverage，不能給未知資料滿分／零分偽裝精確。任一條件有合理缺口時顯示需人工確認。

### V7. AI 投標書健檢／知識庫

- 上傳自家投標書後，依原標案的要求逐項檢查「有無回覆／證據位置／格式或附件缺漏」。
- 用戶可上傳以往標書、公司履約實績、商品型錄／證明等做私有知識庫。
- 生成「回應評選配分的建議大綱」與條款差異，但不得編造公司實績、證照或資格。
- 私有文件必須按租戶隔離、可刪除、紀錄處理來源與保留政策。

### V8. 投標 CRM、行事曆與團隊

- 看板：發現→評估→準備→已投→待決標→得標／未得標／不投。
- 任務：誰負責哪些附件、截止日、完成證據、提醒、留言、審核。
- 日曆：投標截止、現場會勘、簡報、開標及公司自行設定時程。
- 一鍵 CSV/XLSX 匯出投標清單、AI 解析結果及管理報告。
- 公司團隊：席次、角色權限、活動歷史、共用規則與收藏。

### V9. 採購情報 API／MCP（高階選配）

- 給企業 CRM、BI、AI 助理做唯讀查詢；需 API Key、配額、權限與來源署名。
- 不提供不具合法再利用權的原始資料大量轉售。
- 高度依賴官方與第三方資料授權，**P2 之後**再做。

### V10. 不是首期要做的服務

- 人工代標、代寫、顧問協作媒合：需要大量非標準化人工與法律責任，與自助 SaaS 目標矛盾；可先不做。
- 「內定／陪標」判定：高度法律與商譽風險，不能拿公開資料直接標示某機關或廠商違法。
- 「驗收刁難／付款很慢」排行榜：缺乏可核實、同口徑的原始資料時不得實作成客觀評等。
- 自動向官方送件、代繳押標金：不在產品範圍。

| 附件 | 官網合法可下載之規格書／使用者自行上傳 | 不繞過電子領標費用、權限或驗證 |

上線前必須建立 **source_registry**：來源、許可範圍、授權條款、下載方式、更新頻率、最新成功時間、資料種類、可用欄位、是否可保存原始內容／再提供 API。

**資料深度目標**：近期公告可追蹤完整生命週期；歷史案可查多少年應由實際資料品質決定，不承諾已取得某站的千萬筆資料。

## 10. 技術架構與資料模型

### 10.1 建議沿用的低維運架構

```
合法官方資料／獲授權的供應 API
  ↓ 定時擷取 + 最近公告回補
原始快照（來源、時間、hash、授權與擷取狀態）
  ↓ 解析、標準化、同案／版本辨識
主要 DB：案、公告、機關、廠商、投得標、價格、文件索引
  ↓
索引搜尋 + 事先聚合的統計表
  ├─ 公開搜尋 API -> 網頁（GitHub Pages／Cloudflare Pages）
  ├─ 會員 API -> 收藏、規則、投標管線
  ├─ 通知佇列 -> Email、LINE（冪等、退訂）
  ├─ 私有 AI 文件管線 -> 擷取、引用、分析與配額
  └─ ti-support Edge Function -> Gemini／預設回覆／客服工單
       ├─ ti_support_threads / ti_support_messages
       ├─ ti_support_staff / ti_support_admin_owners
       └─ ti_support_daily_quota (全站用量)，is_demo 隔離測試工單
```

可先沿用 GitHub Pages 前端 + Cloudflare Workers 後端 + Turso／其他適用 SQL 資料庫 + 物件儲存，**但不能把 API Token、金流 Secret、LINE 密鑰寫進公開前端或 Git**。資料量放大後要實測搜尋與複合聚合效能；需要時再導入專用搜尋索引（非預設一開始就造大架構）。

### 10.2 核心資料表

- `source_registry`：來源、授權、最後查核日與成功同步日。
- `raw_snapshot`：原始回應、hash、擷取時間、來源 URL。
- `procurement_case`：機關代碼、案號、採購類別與主檔，勿只以案名去重。
- `procurement_notice`：公告 ID、類型、版本、公告日、截止日、官方 URL。
- `case_status_event`：更正、撤銷、無法決標、決標等事件與生效時間。
- `agency`：機關代碼、歷史改制、上級機關、別名。
- `vendor`：統編（可能缺）、名稱、別名、來源信心。
- `bid_party`：每次投標者、得標者、投標價、未得標原因（公告有才填）。
- `award`：單／複數決標、決標金額、標的、底價及契約相關欄位。
- `user_profile` / `company_workspace`：登入、公司輪廓與租戶。
- `watch_rule` / `rule_match` / `notification_event`：監控、匹配、去重與投遞。
- `capture_project` / `task` / `project_document`：投標商機看板、待辦、附件。
- `ai_report` / `ai_credit_ledger`：抽取來源、版本、用量與扣點帳。
- `subscription` / `payment_event`：方案、有效期間、webhook 事件與對帳。
- `ti_support_threads` / `ti_support_messages`：客服 AI 對話、問卷工單、真人站內回覆、使用者歸屬、`is_demo`。
- `ti_support_staff` / `ti_support_admin_owners`：正式客服授權與經驗證的私有擁有者白名單。
- `ti_support_daily_quota`：每日 AI 呼叫／表單總量控制。

### 10.3 不得犯的資料錯誤

1. **案件≠公告**：更正公告可屬同案，但官方一案可能多次更正、重新招標與決標。
2. **招標預算≠底價≠決標金額≠投標價**：歷史分析需保留不同欄位。
3. **得標廠商≠所有投標廠商**：沒有投標全體名單不能做完整同場競爭分析。
4. **無法決標≠一定會重招**；**截止≠已決標**。
5. **機關所在地≠履約地**；同名廠商不一定同統編。
6. 更正公告變動截止日需更新通知與日曆，不能沿用舊日期。
7. 金額未知 NULL ≠ 0 元；來源資料缺漏不能靠 AI 補齊。
8. 原始資料、版本、來源 URL 必須留存，才能重算分析與排查錯誤。

## 11. UI/UX 指引：針對台灣採購公報網的弱點

### 設計目標
- 「3 秒看懂該案狀態、預算、截止日、機關；一點就看到來源」。
- 「查詢首頁優先，不把使用者淹沒在幾十個文字導航連結」。
- 「標案列表可掃讀、可排序、可儲存；詳情不需要跳很多頁」。
- 「手機使用能收藏、開官方連結與設提醒；不用下載獨立 App」。

### 必做互動
- 固定頂端搜尋列：關鍵字 + 常用條件晶片；進階篩選以抽屜展開。
- 結果列：案名／機關／類別／金額／剩餘時間／更正標記／個人適配分數。
- 狀態清楚：可投、已截止待結果、已決標、無法決標、更正等，不濫用綠色。
- 點列表開詳情抽屜（手機滿版），保留原搜尋篩選與捲動位置。
- 右側工作區：收藏、建立監控、加入投標、官方公告、上傳標單。
- 個人化工作台預設只顯示重要動作，資料總覽另放分析頁。
- 無資料時顯示「官方未公開／來源待同步」，不是空白或隨機填假數。
- 完整鍵盤操作、可讀對比、千分位／日期／時區一致，支援 CSV UTF-8 BOM。
- 全站右下角懸浮客服按鈕須兼容手機與桌機；正式客服與示範客服後台必須有清楚區別。
- 未登入網站與會員面板均有「測試帳號一鍵登入」；不要求填 Email／密碼，正式帳戶不能無提醒被替換。

### 文字與信任
- 每個 AI 提示標「資料適配評估，不等於得標機率」。
- 重要數字有「樣本 n、統計區間、計算說明、來源」入口。
- 機關評價只列可證明的採購行為，不能用臆測的「不好合作」標籤。

## 12. 非功能性需求及資安

| 項目 | 目標或政策 |
|---|---|
| 搜尋速度 | 目標 p95 < 1.5 秒（快取命中／合理負載下），需真資料量壓測 |
| 資料新鮮度 | 顯示「官方公告時間」「本站取得時間」「最後成功同步」；目標可用來源 2 小時內更新，達不到不宣稱即時 |
| API | 分頁、查詢上限、速率限制、索引，避免無界掃描 |
| 通知 | 同案同版本同用戶同通路不重複；例外重試、死信與失敗監控 |
| 錯誤處理 | 來源停更或 API 失敗時保留上次可信資料，標明延遲；不得宣稱當日沒案 |
| 可靠性 | 每日自動驗證案件量、金額缺值率、公告版本與當日來源偏差 |
| 隱私 | 私有文件加密、使用者可刪、團隊權限隔離、存取稽核、不得用於未經授權模型訓練 |
| 支付 | webhook 簽章、事件去重、不存卡號、不存密鑰於前端／Git |
| AI | 配額上限、頁碼引用、重試不重複扣點、可人工修正，禁止杜撰公司證照 |
| 授權 | 記錄資料來源授權及再利用邊界；付費層不能繞過資料授權限制 |
| 無障礙 | 鍵盤、焦點、螢幕閱讀器、手機響應 |
| 法律與商譽 | 無違法指控、無「100% 得標」行銷、必要時人工作業複核 |
| 客服資料保密 | 私有客服資料表開啟 RLS，不授權前端直接讀取；Edge Function 每次依訪客 token、Auth ID、正式管理員資格驗證 |
| 測試帳號安全 | Supabase 匿名登入每人獨立 UID；`is_demo=true` 只允許該人操作，不得看真實客服工單或取得正式管理權 |
| AI 客服費用防護 | 金鑰不放前端／公開 Git；缺金鑰不冒充模型推論；限制單一訪客和全站用量 |
| 客服可追蹤性 | 表單提交必須儲存，能查看狀態及真人回覆；失敗時明確報錯，不宣稱假成功 |

## 13. MVP 與迭代順序

## 14. 驗收及市場 KPI

### 14.1 功能驗收案例

1. **同案更正**：先收到新案，再更新截止日；原紀錄保留，只寄一次「截止日變更」，行事曆同步更動。
2. **雙規則重複匹配**：用戶兩條關鍵字都命中同案；Email 不重複寄兩封，列表可標示哪兩條規則匹配。
3. **缺少金額**：來源沒有預算；顯示「未公開」，不在 0 元排序底端假裝便宜案。
4. **公司同名**：兩家不同統編但同公司名稱；不合併投標紀錄。
5. **流標後重招**：以官方案號／機關／公告版本映射；無法確定相同則標「可能關聯」，不是硬併。
6. **來源停更**：停止同步 8 小時，首頁有資料延遲告警而不是 0 新增。
7. **AI 缺頁**：規格書 PDF 掃描品質不佳；回傳哪些頁無法提取，資格規則標待確認，不捏造內容。
8. **AI 解析重試**：網路中斷重試同任務；額度不重複扣。
9. **取消訂閱**：取消後到期前持續有效，到期仍能免費搜尋與保留個人資料（依政策）；不再寄付費通知。
10. **跨租戶權限**：團隊 A 的公司文件與收藏，團隊 B 無法以改 URL 看見。
11. **CSV 注入**：以 "="、"+"、"-"、"@" 開頭的文字欄位不被 Excel 當公式執行。
12. **引用核對**：報表中的廠商、金額、資格和歷史案例都能回到相應來源或標示推論。
13. **缺 Gemini 金鑰的 AI 客服**：送出問題後，顯示「AI 客服功能開發中」，雙方訊息依然寫入資料庫並可在歷史紀錄查看。
14. **問題回報／真人站內回覆**：使用者送出問卷取得工單號；正式管理員可查看、回覆及改狀態；客戶可在網站查看回覆並補充，不走 Email 客服。
15. **訪客／會員工單隔離**：匿名使用者不能讀其他瀏覽器的工單；工單綁定正式會員後不能憑原訪客識別跨帳號讀取。
16. **一鍵登入測試帳號**：不填帳密就建立獨立匿名身分，進入自己的測試客服後台，取得 2 筆示範工單並可重設。
17. **正式／測試隔離**：測試帳號 A、B 不互相看見或改寫工單；也不能看正式工單。正式客服員不會在正式列表看到示範工單。
18. **伺服器權限及配額**：前端不持有密鑰，測試身分不取得正式客服權限；客服表不可被直接匿名讀取，使用量由後端限流。

### 14.2 市場驗證（前 3 個月，目標非保證）

- 先選 1–2 個垂直產業，例如**資訊系統／資安**與**機電設備**；找 10–20 家真實投標廠商做任務導向試用。
- 搜尋成功率：用戶 5 分鐘內找到至少一件確認適合／不適合的案。
- 通知精準度：由使用者標記「真的有關」，逐週追蹤 precision，不以寄出件數當成功。
- AI 解析：抽樣文件的資格／日期／附件漏項率、人工修正成本。
- 轉換：免費→試用→實際付款；續訂率；每家公司每月有多少案進到評估／備標。
- 單位經濟：每位付費用戶的 AI、LINE、Email、資料源、儲存及金流變動成本；避免月費低於邊際成本。
- 至少觀察 2 個完整收費週期才判斷留存，不用官網「有價格」代替市場驗證。

## 16. 最終決策建議

**值得保留全功能願景，但產品開發不要全面同時展開。**

- **先做可靠的免費查詢**，建立 SEO 與信任；別把政府已公開的案名當作付款解鎖賣點。
- **第一個收費產品做「高度個人化雷達＋更正／截止不漏案」**，不用等 AI 才能開始驗證。
- **第二個收費產品做「AI 可引用的資格／評選／交件檢核」**，價值更容易由節省的人力時間衡量。
- **第三個收費產品做「同類比價、機關與對手情報＋投標看板」**，提升續約與企業席次價值。
- **不先進入人工代標市場**：它難規模化，與產品化目標不一致。
- **現有公共監督類「採購異常雷達」保持獨立**；不要用未查核的異常分數影響廠商信用或指控機關。
