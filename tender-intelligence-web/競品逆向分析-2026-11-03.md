# 台灣政府標案平台競品逆向分析與實作方案

> 研究日期：2026-11-03（Asia/Taipei）
> 研究範圍：台灣標案通、標案軍師、標案王、台灣標案雷達；GovTribe 作為美國對照
> 對應本倉庫：tender-intelligence-web/（標案商機情報）、procurement-anomaly-radar-web/（採購異常研究）
> 性質：公開網站、定價頁、FAQ、公開 API 文件與原始碼的「外部可觀測功能分析」。**沒有**登入非本人帳號、繞過存取限制，也沒有取得競品私有後端原始碼、正式客戶數或營收。

## 0. 摘要：先看結論

1. 四個台灣網站都圍繞「政府電子採購網」公告，但資料取得方式與衍生價值不同。
2. **標案王**、**台灣標案雷達**明確說明，採購資料透過 OpenFun/g0v 的 PCC API（pcc-api.openfun.app）取得；**標案軍師**說明來源含政府電子採購網、各地方政府開放資料、經濟部公司登記；**台灣標案通**僅公開說明採政府電子採購網公告，**未揭露**特定 API 或爬蟲技術。
3. 台灣標案通有公開、可直接下單的付費通知方案；標案軍師的個人付費方案於研究日仍標示「敬請期待」，不宜把定價規劃當作已經成交；標案王目前全站免費；標案雷達未觀察到付費方案。
4. 「免費搜尋 + 基本通知 + 廠商排行 + 決標比」已被提供，直接照抄很難形成訂閱優勢。更值得做的是**有證據來源的垂直產業商機評分、變更追蹤、同類案重購預警，以及投標工作流程**。
5. **最大障礙先不是 AI，而是資料授權、完整性、主鍵與公告版本整併**。OpenFun API 的後端程式碼採 BSD 授權，並不代表其中所有政府公告資料取得了相同的商業再利用權；商用要另核對政府開放資料集及原始採購網條款。
6. 本倉庫 tender-intelligence-web/index.html 經檢查仍為**10 筆寫死於 JavaScript 的模擬標案**；沒有即時 API、資料庫、歷史公告清洗或真正的訂閱通知。不能因為介面已有「商機分數」就認為底層資料能力已完成。

### 證據標籤

- **[A] 直接確認**：網站公開頁面、FAQ、定價、原始碼／API 文件明示。
- **[B] 外部觀察**：公開頁顯示功能、欄位、按鈕，但未登入跑通付費或內部流程。
- **[C] 可行實作**：我們要重做相同功能時，合理的技術設計；**不是聲稱知道競品內部怎麼寫**。
- **[D] 待查**：無法驗證資料覆蓋率、內部技術、商業收入或授權，需另行查證。

數量、價格及排程是 2026-11-03 查閱當下網站的**公開宣稱或頁面狀態**；不同網站對「標案／公告／版本」的計數方式不同，不能直接拿總筆數做同口徑比較。

3. **新公告去重**：只通知規則啟用後「第一次看到且尚未截標」的公告。更動條件後重設起算點，避免過去一堆舊案被重新推播。[A]
4. **Email**：付費方案每日 08:05、16:05 彙總；符合件數不限。免費 7 日試用只有一條規則及 08:05 摘要。[A]

6. **追蹤清單**：登入後能追蹤標案、紀錄進度與私人備註；搜尋與機關、決標資料公開。[A]
7. **通知記錄與分析**：中階有 30 日通知紀錄／近 6 個月分析；高階有 90 日／近一年。[A]
8. **CSV**：搜尋條件結果或通知規則命中結果，中階 5 次/月、高階 30 次/月；單檔上限 5,000 筆。[A]
9. **交易流程**：Stripe 處理信用卡、週期續扣；取消後當期用到結束。[A]
10. **內容獲客**：投標流程、資格、押標金、低價與最有利標、服務建議書等教學，有 SEO 搜尋入口。[A]

### 2.4 怎麼做出相同能力 [C，重做方案]

- 基礎資料：採購公告與修正版本入庫；公告 key 與通知規則 key 分離。
- 搜尋：可用 SQL 全文檢索／FTS，依金額、日期、機關代碼建索引。
- 規則格式：rules（user_id、包含詞集合、排除詞集合、機關集合、類別、預算上下限、created_at、enabled_at）。
- 通知：新公告落庫後執行規則匹配，寫入 matches；對每個（rule_id, publication_id, channel）建唯一鍵，保證重跑不會重寄。
- 變更規則時建立新 rule_version 或更新生效時間；不要反覆通知既有舊案。
- 發信：Email provider + webhook 接收退信／退訂；LINE Messaging API 綁帳號、退訂與頻率限制；Stripe webhook 處理付款有效期及方案權限。
- 網頁：搜尋頁不需付費，付費點放在「規則數量、發送頻率、追蹤歷史、團隊協作、變更與截標提醒」；這是**建議的重做架構，不代表它們現在實際使用的技術**。

**可學之處**：規則條件與投遞節流非常具體，是可重做的產品規格。
**不值得照抄**：單純 Email 摘要可替代性高，而且台灣其他站免費提供。

### 3.4 怎麼重做 [C]

- 對資料庫先建完整公告、年度採購與投得標關係，再做結構化指標。
- AI 最適合用在**使用者上傳的招標文件**，因為需求明確、可引用頁碼／條款、節省人工時間，且可按份計費。
- 文件管線：安全上傳（大小／掃毒／私有儲存）→ PDF/Office 解析 → 分頁／段落／表格與標題切塊 → 結構化欄位抽取 → 每項「資格／評分／交件／時程」附來源頁碼 → 使用者確認 → 生成 Excel 檢核清單。
- Go/No-Go 先使用明確規則：資格不符、截止太近、保證金不足、實績不足作硬性提醒；競爭程度、毛利、契合度由使用者補資料，給出**依據**而非「必勝概率」。
- 價格分析：同類案件樣本群、不同決標方式分層、最低樣本數、去除跨年份／不同規模不適配對比，輸出分布與樣本連結；避免 AI 在沒有有效統計資料時編造底價。
- 知識庫必須做 tenant 隔離、權限、文件刪除、審計及避免資料外洩。

**可學之處**：真正的付費位置可能在投標工作流、標書拆解，而不只是搜尋。
**疑點**：收費尚未正式公開、歷史數據描述彼此不一致，使用者案例在網站明示為情境示意，非證實客戶成績。

## 4. 標案王 — www.bidking.tw

### 4.1 資料從哪來

- [A] 站方 FAQ **明確寫**：政府電子採購網，透過 https://pcc-api.openfun.app/ 公開 API 取得。
- [A] 平日 02:07／12:07／18:07（台北時間）自動更新。
- [A] 2024 年起為較完整資料；2020–2023 是歷史摘要，欠缺預算及決標金額，全文搜尋只涵蓋 2024 年起。
- [A] 研究日首頁宣稱自 2024 年起收錄 567,604 件，另有 2020–2023 回溯摘要。這是**站方計數**，非獨立抽樣稽核。
- [D] 無法只憑「使用 API」判定它是直接查詢 API、定期抓取進自己的 DB，或使用何種正式部署技術。

### 4.2 已公開功能

1. **標案搜尋**：查標案、機關、投標與得標公司，提供官方公告連結。
2. **即將截標**：依截止日排序。
3. **廠商投標／得標紀錄**：用公司名或統編查歷史。
4. **競爭對手分析**：同場投標的廠商、雙方勝負與共同得標次數。
5. **無法決標專區**：找失敗／未決標案，觀察可能重招的機會。
6. **關鍵字訂閱**：Email、關鍵字、縣市，平日 07:11 摘要，可退訂。
7. **機關發包排行**：依機關歷史發包分析。
8. **小額接案專區**：為小型供應商提供專門入口。
9. **統編公司檔案**：整理公司的投標／得標相關資料。
10. **決標價比**：決標金額 ÷ 預算，按機關、工程／財物／勞務及預算區間計算平均、中位數及分位分布。
11. **週期標案預告**：有「未來 60 天可能出現的標案」專區，**屬預測，不是已公告案件**。
12. **分類導覽**：地區、預算、機關、產業主題（如清潔、資訊、委託研究）。

### 4.3 可再現的核心算法 [C]

**決標價比**：
- ratio = award_amount / budget_amount。
- 限定分子分母皆有值、預算 > 0；同案不同版本不得重複入樣；分組後給出樣本數、平均、中位數、25%～75%區間。
- 站方分析頁在研究日宣稱 123,169 個可計算樣本，另排除 37 筆比例 0 或 >1.5 的異常值；這是它的樣本設定，不應照抄成普遍的資料清洗真理。>1 可能因增購、契約或資料口徑而有合理原因，須另列分析。
- **不可以把「決標價比」當成「投標廠商勝率」或「決標價／官方底價」；三者不同。**

**同場競品**：
- 需要每個採購案件的實際投標廠商列表，不是單靠得標人推算。
- 兩廠商出現在同一「可比較投標事件」才計同場；共同投標、複數決標、限制性招標另有規則。
- 如果資料只有「得標廠商」沒有所有投標廠商，**就不能做完整同場分析**。

**週期標案預告**：
- 依機關、標案類型、商品與歷史年度形成可比較序列；觀察發包間隔與上一件契約期限。
- 輸出下一個可能公告期間、樣本年份、可信度、歷史來源連結；不是承諾一定重招。

### 4.4 商業模型

- [A] FAQ 目前顯示**所有查詢、分析、關鍵字電子報免費，免註冊**。
- 另有維護單位「仁禾管理顧問」提供投標策略及補助申請接洽管道，但**無法確認**網站流量轉為多少服務收入。

## 8. 如果我們自己做：技術架構與 PRD 建議

### 8.1 先不直接改現有 MVP；資料層與前端分開

本倉庫現狀：
- tender-intelligence-web/index.html：HTML/CSS/JS 單檔，10 筆 tenders 陣列為寫死模擬資料；分數以常數 score 加上產業匹配 +5/-9 調整，沒有真實機關或歷史紀錄計算。瀏覽器 localStorage 保存追蹤，CSV 只匯出模擬陣列。
- procurement-anomaly-radar-web/README.md：已明確定義異常**只作人工查核優先度**，而非違法結論；現有原型同樣不應誤當正式驗證完成。
- 本研究只新增 Markdown，**沒有更動程式、資料庫、GitHub Actions、網站部署或生產資料**。

### 8.2 建議可持續擴張的資料流程 [C]

~~~text
合法資料來源（官方 JSON/XML；許可的 API；其他取得授權資料）
  -> 原始回應留存（append-only、來源 URL、時間、hash、授權類型）
  -> 統一欄位／單位／時區／主鍵
  -> 公告版本與單一採購案件整併
  -> 主資料庫（PostgreSQL/Turso 均可視容量和查詢選型）
  -> 搜尋索引 + 預先彙整的機關/廠商統計
  -> API（分頁/快取/查詢）
  -> 網站 + 儲存搜尋 + 通知 + 追蹤 CRM
  -> AI 文件拆解（使用者合法上傳的附件；可核對頁碼）
~~~

**不推薦**每個使用者搜尋時即時向第三方 API 全庫查詢，也不推薦前端下載全國 JSON 後在瀏覽器篩選。前者不可控，後者資料量成長會很慢。

### 8.3 建議 schema（概念表）

| 表 | 重要欄位 |
|---|---|
| source_registry | id、provider、dataset_url、license、commercial_use_status、checked_at |
| raw_publication | source_id、source_key、fetched_at、payload_hash、raw_ref、parse_status |
| procurement_case | case_id、authority_id、case_no、title、category、procurement_method、first_seen_at |
| procurement_notice | notice_id、case_id、notice_type、notice_date、deadline_at、original_url、version、raw_id |
| case_status_history | case_id、status、effective_at、notice_id、observed_at |
| procurement_award | award_id、case_id、award_date、award_amount、budget_amount、decision_method |
| bidding_party | award_id／case_id、vendor_id、role（bidder/winner/failed/joint）、source_notice_id |
| agency | agency_id、agency_code、name、parent_id、aliases、valid_from/to |
| vendor | vendor_id、company_id_nullable、name、aliases、identifier_confidence |
| saved_rule / rule_match / notification_log | rule_id、version、filters、matched_notice_id、channel、sent_at、delivery_status |
| document_analysis | file_id、case_id、tenant_id、extraction_version、citation_page、result_status |

關鍵：
- **procurement_case（採購案件）≠ procurement_notice（公告）**：一案可以多次公告、更正、流標、決標。
- **award_amount（總決標金額）≠ budget_amount（預算）≠ reserve price（底價）**。
- **bidder（投標）≠ winner（得標）**；只存得標人就無法推出所有同場競爭者。
- 公司統編常缺漏、機關改制，必須有來源、別名及可信度資訊。
- 保存原始公告及解析版本，才能在解析器修正後重算歷史資料。

第一個版本不一定要 Elasticsearch。若資料是十萬至數百萬公告，可先用 PostgreSQL 索引／FTS 或合適的嵌入式搜尋方案測實際 p95，只有確認瓶頸才導入專用搜尋服務。Turso 若用於交易與查詢，全文與多維聚合能力要先做負載驗證，不能靠假設。

### 8.5 六個核心功能怎麼做

**A. 搜尋與最新公告**
- 後端按日期增量拉取，對最近 30–90 天反覆回補，以抓到更正和延遲的決標資料。
- 對每次回補用（source + notice ID/hash）做 idempotent upsert。
- 實際狀態以官方公告與截止日判斷，**截止日已過不代表已決標**。

**B. 廠商／機關畫像**
- 按 agency_id、vendor_id、年份、公告類型聚合；投標／得標分開統計。
- 展示分母：投標幾件、已決標幾件、有記載投標廠商幾件；資料缺漏會造成勝率偏差。

**C. 決標比與報價**
- 只對可比較案件算分布；按採購方式、決標方式、類別、預算帶與年份區分。
- 展示 n、median、IQR、例外值與來源，不直接說「推薦投標價 = 中位數 x 預算」。

**D. 重購機會**
- 以履約期、契約年限、續約選項、實際再次招標序列判斷；若只有時間間距，標為「可能週期」而非確定預告。
- 有足夠可比案例才給區間，無資料則不預測。

**E. 產業商機評分**
- 客戶先填自己能做的商品、履約地、最小/最大可接金額、必要資格與實績。
- 硬性排除：法定資格明顯不符、已截止、地區無法履約等。
- 軟分數：文字語意、歷史得標類別、預算規模、準備時間、競爭強度；每一分數要有計算依據。
- 不使用「AI 預測 95% 得標機率」這種未經驗證敘述。

**F. 通知與投標工作流**
- 搜尋保存 → 首次新公告 → 更正提醒 → 截止倒數 → 決標後跟進。
- 事件與發送分離，佇列重試、唯一鍵防重寄、每天限額、退訂記錄。
- CRM 最小欄位：是否要投、業務負責人、下一步、文件截止、最後更新。
- 有文件上傳才啟用 AI 拆解，輸出可核對條款與附件缺項清單。

### 8.6 分階段落地與驗收

| 階段 | 交付 | 過關標準 |
|---|---|---|
| P0 資料合法性 | 來源／授權矩陣、樣本下載與欄位地圖 | 商用路徑明確、缺漏可見、無繞過限制 |
| P1 真資料接入 | 30 日增量、90 日回補、原始快照與主鍵 | 重跑不重複、同案可查全部公告版本、有官方 URL |
| P2 免費競品等級 | 搜尋、標案詳情、廠商與機關、CSV、RSS | 查詢速度可接受、數字與官方抽樣核對 |
| P3 收費 MVP | 產業規則、有效 Lead、Email／LINE、追蹤、改版通知 | 投遞防重、退訂運作、能監測實際點擊與採用 |
| P4 付費差異化 | 同類採購、重購提示、標書解析、Go/No-Go | 每個指標可回溯、AI 輸出附來源頁碼 |
| P5 成本與規模 | 方案權限、費率、企業多席位、維運監控 | 首批真付費及續用；來源中斷不造成假資料 |

### 8.7 該怎麼定位才有收費空間

- **不要只做另一個標案搜尋器**：標案王免費，標案軍師連 LINE 都免費。
- **建議主攻一個垂直產業**（例如資訊系統整合／資安／機電設備），把產業資格、過往得標、機關偏好、相似規格、重購訊號做深。
- 免費層：搜尋、官方公告連結、基礎統計。
- 付費層：高精度匹配、即時更正與截止通知、同類重購、專屬追蹤清單／多人分工、文件拆解。
- 先找 10 家真正有投標經驗的廠商驗證：每月能找出幾件**真的能投**的標案，以及是否能替它們省備標時間，再決定正式收費。
- 所有價格與市場大小在沒有成交證據前只能視為**待測假設**。

## 10. 還不能從公開資料得出的答案

以下**沒有**因研究而變成已知，不應對外宣稱：

- 四家競品實際 DB schema、雲端廠牌、排程平台、程式框架、爬蟲程式與代碼。
- 每一家的正式收錄完整率、每小時實際成功率、歷史資料準確度，除非另有抽樣驗證。
- 任一競品實際會員數、付費戶數、營收、利潤、獲客成本、續訂率。
- 標案軍師目前未開售的 Pro / Team 方案有多少真實付費客戶。
- OpenFun 提供 API 就必然賦予我們對所有政府電子採購網資料的商業再授權。
- 任何底價「預測」能夠得知未公開的官方底價或保證中標。

**最終建議**：先把合法可用的官方資料和 OpenFun 介接、授權策略徹底釐清，再將現有的標案情報 MVP 由「寫死模擬資料」升級為「可追溯的真實公告歷史 + 產業商機匹配 + 變更通知」。採購異常雷達維持獨立領域與非指控式表述，不要混入投標服務的對外評分。
